## domain/ — pure business logic (no Ink dependency)

### `domain/attachments.ts`
Composer tokens (`[[ Image N ]]`, paste snippets) are literal text sitting inside the textarea value — not a separate data structure glued to the UI. `imageToken(index)` formats the label; `nextImageIndex` finds the next free index by scanning existing tokens; `droppedTokens` diffs live text against tracked tokens to detect user-deleted attachments (deleting the bracketed text IS the removal UI — no separate delete button); `expandTokens` is a closure that, at submit time, walks the paste-snippet regex left-to-right and swaps each token for its real payload (image tokens expand to nothing — the image rides out-of-band in `session.attached_images` — and consume one adjacent space so deletion doesn't leave a double-space).
**Go/Bubbletea note**: Atlas's textarea doesn't support this pattern yet. If Atlas ever supports paste-collapsing or image attachment, model it the same way: a plain-text placeholder token embedded in the buffer, with an out-of-band map from label→payload, expanded only at submit. Cheap to implement and gives you free cursor/selection/backspace support since the token is ordinary text.

### `domain/blockLayout.ts` — **HIGH VALUE, read fully as flagged**
This is the transcript's "gap iff a new visual group opened" algorithm.
- `BlockGroup` enumerates 8 visual bands: `user | model | trail | note | diff | slash | intro | event`.
- `messageGroup(msg)` maps a message to its band by `kind` first (intro/panel→intro, slash→slash, event→event, diff→diff, trail→trail), then falls back to `role` (user→user, assistant→model, else→note).
- `SELF_SPACED` = `{diff, event, intro, slash, user}` — these bands own their own margins elsewhere (e.g. user turn separator) and never get an extra leading gap from this algorithm.
- `PAINTS_TRAILING_GAP` = `{diff, event, user}` — these already paint a blank line *below* themselves, so the next block must not double up.
- **The core rule** (`hasLeadGap`): a block gets exactly one blank line above it **iff** its group differs from the immediately-preceding rendered block's group, is not self-spaced, and the predecessor doesn't already paint a trailing gap. This is computed **only from the predecessor's group**, never the current block's own (possibly still-streaming) content — so a live-streaming assistant block computes the identical gap as the same block does once settled. No layout jump when a message finishes streaming.
- `blockRenders(msg, ctx)`: a `trail` block (reasoning+tools) is invisible ("renders nothing") when it has no todos/tools/thinking, or when every section (`thinking`/`tools`/`activity`) is set to `hidden` via `/details`. Every other kind always renders.
- `prevRenderedMsg`: walks backward past invisible trail blocks to find the real grouping predecessor, so a hidden/empty trail never introduces a floating gap, doesn't double the gap after a user prompt, and doesn't pad space above the final reply.

**Go/Bubbletea translation**: This is directly portable and is probably Atlas's single highest-leverage visual fix. Implement as a pure function `hasLeadGap(prevGroup, curGroup) bool` fed by a `messageGroup(msg) Group` classifier, called while building the transcript's rendered string (or per-viewport-item list). Key discipline to preserve: (1) the decision must depend only on the *previous* rendered item's group, not on live/mutable state of the current item, so a streaming reply's spacing never flickers on completion; (2) skip empty/hidden items when finding "previous" so a collapsed section never introduces a spurious gap.

### `domain/composerHighlights.ts`
Composer syntax highlighting is a pure tokenizer: scans the input text for 3 span types — paste/image tokens (`[[ ... ]]`), `@refs` (`@file:`, `@diff`, quoted values, half-typed), and `/slash` references (leading OR **mid-prose** — a bare `/skill` name dropped into a sentence). On overlap, earlier-detected kind wins (so a slash inside a quoted `@ref` value stays part of the ref). `splitComposerHighlights` returns ordered `{ref, text}` segments that concatenate back to the exact original string (styling only, text never rewritten). `highlightMask` turns that into a per-character boolean array. `highlightsStable(prev, next)` checks whether every surviving character keeps its highlight state — used as a fast-path gate: if stable, the renderer can just append the new characters' styling instead of a full repaint.
**Go note**: Directly reusable regex-ordering trick if Atlas ever highlights `/commands` or `@refs` in its input. The "first-match-wins on overlap" + "reconstruct exact string" contract is the reusable idea.

### `domain/details.ts`
Implements the 3-state `hidden|collapsed|expanded` details mode plus **per-section defaults that layer above the global mode**: `thinking` and `tools` default to `expanded` (so the transcript reads as a live process by default) while `activity` (ambient gateway hints) defaults to `hidden`; `subagents` has no built-in default and falls through to global. `sectionMode(name, global, sections, commandOverride)` resolution order: explicit per-section override → (if `/details` command explicitly set) global → built-in default → global. `nextDetailsMode` cycles hidden→collapsed→expanded→hidden for a toggle keybinding.
**Go note**: Atlas likely has a single global verbosity toggle. Hermes's insight — thinking/tools default open, ambient noise defaults hidden, independently of the global cycle — is a good UX default to copy even without full per-section config: default to showing tool calls/reasoning live, and suppress low-value system chatter separately from that toggle.

### `domain/messages.ts`
`userDisplay(text)`: long user messages (>300 chars, `LONG_MSG` in config/limits.ts) collapse to a short label — first line, first 4 words (or the whole first line if it's one word), max 80 chars, suffixed `[long message]`. `toTranscriptMessages(rows)`: converts raw transcript rows into `Msg[]`, folding consecutive `role:'tool'` rows into a `pending` string array attached to the *next* assistant message's `.tools[]` (tool results don't get their own bubble — they ride along with the reply that follows them), and converting special `display_kind` markers (`hidden`, `model_switch`, `auto_continue`, `personality_switch`, `async_delegation_complete`) into dim system `event` rows instead of normal chat bubbles. `fmtDuration(ms)`: `Xh Ym` / `Xm Ys` / `Xs` — clean tiered duration formatter.
**Go note**: The tool-trail-folds-into-next-assistant-message pattern and the long-message truncation heuristic (words not chars, capped at 80) are both easy, worthwhile ports.

### `domain/paths.ts`
Status-bar text-budget formatters, all pure string functions: `shortCwd` (home-dir `~` substitution, then `…`-truncate from the front, keeping the tail — the *end* of a path is usually more informative than the start); `fmtCwdBranch` (appends `(branch)` and shrinks the cwd budget to make room, truncating the branch itself from the front if it's long); `shortProject`; `fmtProjectCwdBranch` (project name is prioritized over cwd/branch when space is tight — full drops to project-only under 8 chars remaining); `composeTabTitle` (terminal titlebar string, ` · `-joined segments, `marker` glued with a plain space not a separator).
**Go note**: Directly and cheaply portable to Atlas's status bar. The "truncate path from the front, keep the tail" and "shrink budget for extra segments rather than hard-cutting" patterns are exactly the kind of polish Atlas's status bar is missing.

### `domain/providers.ts`
One tiny function: `providerDisplayNames` disambiguates providers that share a display name by appending `(slug)` only for the duplicated ones — a de-dup-on-demand label formatter for a model/provider picker list.

### `domain/slash.ts`
`TUI_SESSION_MODEL_FLAG = '--tui-session'` and `sessionScopedModelArg` — strips any existing `--global`/`--session`/the TUI flag from a raw arg string and re-appends `--session`, used when a TUI picker (model, etc.) needs to force session-scoping before handing the string to the backend's `config.set`. `looksLikeSlashCommand` = `/^\/[^\s/]*(?:\s|$)/` (leading slash, no embedded slash before the first space/EOL). The big one: `INLINE_SLASH_RE = /\s\/([a-zA-Z][\w-]*)?$/` and `inlineSlashTrigger` — detects a **mid-prose** `/skill` reference (must be preceded by whitespace, single bare segment, ends at the caret) so a user can type "clean this up with /clean" and get skill-name completion without it being treated as a command invocation (that's reserved for position 0). `parseSlashCommand`, `applyCompletion` (replaces from a given offset, dropping a duplicate leading slash), and `completionToApplyOnSubmit` — the subtle one: Enter should NOT swallow a completion that merely appends trailing whitespace to an already-complete command (e.g., `/exit`→`/exit ` for a legacy dropdown-open convention) or every slash command would need 3 Enters instead of 1-2.
**Go note**: If Atlas ever supports inline `/skill` references (not just command-position slashes), the "whitespace-preceded, single-segment, caret-anchored" regex approach avoids false positives against paths like `/usr/local`. The Enter-vs-completion edge case is a genuinely subtle bug class worth pre-empting if Atlas builds a completion popover.

### `domain/usage.ts`
Trivial: `ZERO: Usage = {calls:0, input:0, output:0, total:0}` — a zero-value constant for the usage struct, avoids re-allocating/re-typing zeros at call sites.

### `domain/viewport.ts`
`stickyPromptFromViewport` — powers a "sticky last-prompt" label pinned to the top of the transcript viewport while scrolled up: given a virtualized list, binary-searches (`upperBound`) into a prefix-offset array to find which messages are currently visible, and if the visible window does NOT include a user message (i.e., you've scrolled deep into a long assistant reply), walks backward to find the most recent user message that scrolled *above* the top and returns its collapsed label (single-line, whitespace-collapsed). Returns empty string when at the bottom (`sticky`) or when the visible range already contains the user turn itself.
**Go note**: This is the mechanism behind "you're mid-reply, here's what you originally asked" headers some TUIs show. Directly relevant if Atlas's viewport ever scrolls independently of the live tail — nice low-cost orientation aid for long streamed replies.

## hooks/

### `hooks/useCompletion.ts`
The full completion request pipeline. `completionRequestForInput(input)` decides between 3 request shapes: `complete.path` (file-path completion via `TAB_PATH_RE`, a broad regex matching quoted/unquoted paths, `~/`, `../`, `@`-prefixed, drive letters), `complete.slash` at position 0 (full command completion, `replaceFrom:1`), or `complete.slash` **mid-prose** with `skillsOnly:true` (via `inlineSlashTrigger` from domain/slash.ts — only skills are valid mid-sentence references, since built-ins like `/model` don't make sense embedded in prose). `/model` is special-cased to return `null` (no inline completion) because it uses a separate two-step `ModelPicker` UI instead. The hook itself: 60ms debounce (`setTimeout`), a `ref.current` guard so a stale in-flight response never overwrites state for a newer query, and a `mergeWidgetAppItems` step that appends locally-registered widget-app slash commands (e.g. `/ticker`, `/weather`) to the gateway's own completion list, ranked by a fuzzy matcher (`rankSlashItems`) that also matches against each app's **description text**, not just its id — so `/timer` can surface a widget whose help text mentions "timer" even if its id doesn't start with "timer".
**Go note**: The 60ms debounce + stale-response guard pattern (compare `ref.current` before applying results) is the standard fix for completion-race flicker; worth confirming Atlas's own completion path (if any) has this guard. The client-side-registry-merged-into-server-completions pattern is relevant only if Atlas builds its own plugin/widget system.

### `hooks/useGitBranch.ts` — **directly answers "no git branch in Atlas's status bar yet"**
```go
// Go translation sketch
TTL := 15 * time.Second
TIMEOUT := 500 * time.Millisecond
```
Uses `execFile('git', ['-C', cwd, 'rev-parse', '--abbrev-ref', 'HEAD'], {timeout: 500ms})`, treats `''` or `'HEAD'` (detached) as "no branch" (`null`), and caches per-cwd with a 15s TTL plus an in-flight dedup map (`inflight`) so concurrent calls for the same cwd share one subprocess instead of spawning N gits. A `setInterval` refreshes every 15s while mounted; state seeds synchronously from cache on first render (no initial flash), then updates async once the process resolves. Total surface: ~35 lines.
**Go note**: This is a small, self-contained, high-value port. In Go: `exec.CommandContext(ctx, "git", "-C", cwd, "rev-parse", "--abbrev-ref", "HEAD")` with a 500ms timeout, a `map[string]cachedBranch{at time.Time, branch string}` keyed by cwd with 15s TTL, refreshed on a ticker or lazily on next status-bar render if stale. Cheap addition to Atlas's existing cwd/duration/tokens status bar segments — the `paths.ts` `fmtCwdBranch`/`fmtProjectCwdBranch` formatters above are the natural companion pieces (truncate branch from the front if long, shrink cwd budget to fit).

### `hooks/useInputHistory.ts` — **directly answers "no arrow-key history in Atlas's textarea"**
Tiny (12 lines): holds a `historyRef` (loaded once via `inputHistory.load()`, from `lib/history.js` — not in this file's fetched slice, but presumably reads a persisted history file), a `historyIdx` (null = not currently navigating history — i.e., you're on your live draft), and a `historyDraftRef` (the in-progress draft the user was typing before they pressed ↑, so pressing ↓ back past the oldest history entry restores exactly what they were mid-typing, not an empty string). `pushHistory` is just re-exported `inputHistory.append`. All the actual up/down-arrow *behavior* (index math, draft-swap logic) is NOT in this hook — it lives in whatever consumer wires these refs into keypress handling (not in this file's fetched slice; likely `app/useMainApp.ts` or the composer component, out of this agent's assigned scope).
**Go note**: The pattern worth copying even without seeing the consumer: (1) persist input history to a file across sessions, (2) `historyIdx == nil/-1` sentinel meaning "not browsing, this is live text", (3) preserve the user's uncommitted draft before entering history-browse mode so ↓ past the bottom restores it rather than clearing the field. Implementation for Atlas: track `historyIndex int` (-1 = live), a `draftBeforeHistory string` snapshot taken on first ↑ press, and a `[]string` ring loaded from `$XDG_STATE_HOME/atlas/history` or similar, appended on submit.

### `hooks/useQueue.ts` — **directly answers "Atlas ignores input while streaming; Hermes queues it"**
A full message-queue implementation, ~110 lines, all pure-ish with a `useRef` backing array (mutated in place for perf, mirrored into `queuedDisplay: string[]` state for rendering) plus a separate "currently editing a queued item" index (`queueEditIdx`). Key operations: `enqueue(text, display)` (push), `prependQ(item)` (unshift — used for "put this back at the front" scenarios), `dequeue()` (shift — pull the next queued message when the current turn finishes), `takeQ(i, editedDisplay)` (splice out item `i`; if the caller also passed edited display text, it substitutes the edited portion back into the underlying `.text` payload via a naive string-replace of the old display substring — so editing a queued item's visible text also updates what actually gets sent, as long as the edited text still contains the original display substring), `removeQ(i)` (delete without re-adding). All queue mutation funcbs re-sync the `queuedDisplay` array afterward so the render layer always reflects `queueRef.current`.
**Go note**: This is the single most impactful UX feature flagged in the manifest. Atlas currently blocks/ignores keystrokes while a turn streams — Hermes instead lets the user keep typing and hit Enter to **queue** additional messages, which drain one at a time as each turn completes (dequeue happens elsewhere, likely in `app/turnController` outside this slice, on turn-complete). Minimal Bubbletea port: a `[]queueItem{text, display string}` slice on the model, `Enter` during a busy state calls `enqueue` instead of submitting to the LLM, the queue renders as a small stacked list under/above the composer (Hermes shows `queuedDisplay` — plain visible text, so the user can see what's pending), and on stream-complete the app pops the head and submits it automatically. The "editable queue item" (`takeQ` with `editedDisplay`) is a nice-to-have but the base enqueue/dequeue/render loop is the 80/20 value.

### `hooks/useVirtualHistory.ts` — long (690 lines), heavy perf-tuned virtualization engine
This is Hermes's transcript virtualizer — analogous to what Atlas would need if its transcript grows large and full re-render becomes slow. Key ideas, independent of the Ink/Yoga-specific plumbing:
- **Overscan + hard mount cap**: renders `viewport + overscan` items around the visible window, capped at `MAX_MOUNTED = 120` regardless of scroll position, to bound worst-case DOM/render-tree size.
- **Coverage guarantee**: after computing a mount range, it keeps growing the range (using a **pessimistic height floor of 1px per unmeasured item**) until total estimated height ≥ viewport+2×overscan, so the viewport is never under-covered by wrongly-small estimates.
- **Slide-step throttling on fast scroll**: detects scroll velocity (`|ΔscrollTop| + |pendingDelta| > 2×viewport`) and caps how many *new* items can mount per commit (`SLIDE_STEP=12`) — prevents a single PageUp-into-unmeasured-territory from mounting/measuring ~190 rows synchronously (they measured this as ~600ms of jank without the cap).
- **Binary-search offsets**: a monotonic `Float64Array` prefix-sum of item heights, rebuilt only when a height cache write bumps a version counter — binary search replaces an O(n) linear scan that was ~2ms/render at 10k+ items.
- **Deferred range growth** (`useDeferredValue`): the *urgent* render keeps painting the OLD (already-measured, cheap) mount range while a background/deferred render computes the NEW range (which requires fresh markdown/syntax-highlight work) — avoids blocking the main thread during scroll.
- **Measure-at-unmount**: captures a node's final computed height in its cleanup ref callback (before the underlying layout node is freed) rather than only in a mount-time layout effect, so scrolling an item out during fast panning doesn't leave a stale height estimate.
- **Width-resize height rescaling**: on a terminal resize, existing cached heights are *scaled* by the old/new column ratio instead of being invalidated outright (avoids a full expensive re-measure pass), then "frozen" for 2 renders while the real (post-resize) heights settle in behind the scenes.
**Go note**: Full virtualization is only worth porting to Atlas if/when transcript re-render becomes a measured bottleneck — this is a lot of complexity purely in service of avoiding React/Yoga layout costs that don't exist in Bubbletea's render model (Bubbletea has no persistent widget tree to mount/unmount; each `View()` call is a fresh string build). The one universally-relevant idea, even for a from-scratch string-builder transcript: **cap how much of the transcript you re-render per frame during fast scroll**, and **cache line-wrapped/height-computed content per message keyed by content+width**, invalidating only on actual resize — i.e., memoize the expensive part (word-wrap + glamour render) per message rather than recomputing on every keystroke/frame.

## config/

### `config/env.ts`
Startup env-var resolution, all pure parsing with clear precedence chains documented in comments (not repeated here at length): `TERMUX_TUI_MODE`, `STARTUP_RESUME_ID`/`STARTUP_QUERY`/`STARTUP_IMAGE` (session resume/prefill via env), `MOUSE_TRACKING` mode resolution (`HERMES_TUI_MOUSE_TRACKING` explicit override → `HERMES_TUI_DISABLE_MOUSE` legacy kill-switch → Termux defaults mouse off (touch conflicts with terminal mouse protocols) → desktop defaults `'all'`), `NO_CONFIRM_DESTRUCTIVE`, `DASHBOARD_TUI_MODE` (narrower than inline mode — a browser-embedded PTY host has no restart path so this also disables Ctrl+C-as-SIGINT later in `entry.tsx`), `DEV_CREDITS_MODE` (dev-only live-spend readout), `INLINE_MODE` (skip AlternateScreen so native terminal scrollback captures history — Termux defaults this on for backgrounding-friendliness), `SHOW_FPS`.
**Go note**: The precedence-chain-with-explicit-override pattern (specific override > legacy flag > platform-detected default) is a reusable config-resolution idiom worth mirroring in Atlas's own env/flag parsing if it grows similar knobs.

### `config/limits.ts`
```
LARGE_PASTE = {lines: 5}
LIVE_RENDER_MAX_CHARS = 16_000, LIVE_RENDER_MAX_LINES = 240   // live-streaming render budget
VERBOSE_TRAIL_MAX_CHARS = 800, VERBOSE_TRAIL_MAX_LINES = 12   // persisted per-tool-call preview budget (much smaller!)
LONG_MSG = 300           // userDisplay() truncation threshold, see domain/messages.ts
MAX_HISTORY = 800        // max transcript messages kept
THINKING_COT_MAX = 160
WHEEL_SCROLL_STEP = 1
```
The comment on `VERBOSE_TRAIL_MAX_CHARS` is a genuinely important war-story: persisted tool-trail blocks used to render at the *live* budget (16KB) for **every** historical tool call simultaneously, and a session with heavy browser/large-output tool use could retain ~12MB of strings that exploded into "a few hundred MB" of render-tree nodes and silently OOM-killed the process (issue #34095 in their tracker). Fix: cap the *persisted* per-call preview to 800 chars / 12 lines (full output stays in agent context + SQLite, this is just "a glance, not a log"), while the *live streaming tail* keeps the larger 16KB budget.
**Go note**: Directly relevant risk for Atlas — if Atlas renders full tool output inline for every historical tool call in the transcript (not just the live one), long sessions with big tool outputs (file reads, browser dumps) could bloat memory/render time the same way. Worth auditing: does Atlas cap the *persisted* preview size independently from the *live* streaming size? If not, add a small constant (e.g. 800 chars / 12 lines) for settled tool-call blocks specifically.

```
STREAM_BATCH_MS = 16, STREAM_IDLE_BATCH_MS = 16   // ~60fps batching of streaming token deltas
STREAM_SCROLL_BATCH_MS = 96                        // batch scroll-follow updates slower than content updates
STREAM_TYPING_BATCH_MS = 80
TYPING_IDLE_MS = 250
REASONING_PULSE_MS = 700
RESIZE_COALESCE_MS = 32     // coalesce SIGWINCH burst from drag-resize to ~30fps
DOUBLE_ESC_MS = 500         // double-Esc-to-discard-draft window
```
The `RESIZE_COALESCE_MS` comment explains why: a drag-resize can fire one SIGWINCH per pixel step on some terminal hosts, and each distinct width remounts/re-measures the visible rows, so reflowing on every tick stutters visibly — coalescing to ~30fps keeps it responsive but smooth, always landing the final width on the trailing edge.
**Go note**: If Atlas re-wraps/re-renders on every raw resize event from Bubbletea's `tea.WindowSizeMsg`, consider a similar debounce (~30ms) for the *reflow* work specifically (the resize itself can update dimensions instantly; defer the expensive re-wrap). `DOUBLE_ESC_MS = 500` and the double-Esc-discards-draft convention (shared with Claude Code / Gemini CLI per the comment) is a cheap, already-familiar-to-users affordance worth copying verbatim if Atlas doesn't have it.

### `banner.ts`
Startup banner rendering: `parseRichMarkup` parses a **very** limited rich-text markup — `[#hexcolor]text[/]` or `[bold #hex]text[/]` or `[dim #hex]text[/]` spans — into `[color, text]` line-segment tuples, used to let a skin author a fully custom banner as a small color-tagged markup string instead of an ASCII-art array. **Go note**: The "gradient via a hand-authored per-line palette-index array over N flat theme colors" trick is a cheap, effective way to make static ASCII art feel less flat without computing a real color ramp — directly applicable if Atlas has (or wants) a startup banner: pick 3-4 theme tones, hand-assign an index per line (e.g. top rows get `primary`, middle `accent`, bottom `muted`) rather than trying to interpolate a smooth gradient.

### `entry.tsx` — process entrypoint, defensive/operational hardening
Notable patterns, roughly in order of relevance to a Go TUI:
1. **Terminal-mode reset on `process.on('exit')`** as a hard backstop — not just on graceful signals. The comment explains a real regression (#28419): every other cleanup path (`/quit`, Ctrl+C, Ctrl+D, any `process.exit()`) left DEC mouse-tracking escape sequences (`?1000/1002/1003/1006`) armed in the parent shell, causing garbage mouse-report bytes (`102;71M5;104;62M`-style) to leak into the next thing that reads stdin (the shell itself, or a freshly relaunched TUI mid-init). Fix: register `process.on('exit', resetTerminalModes)` as a final synchronous backstop, since `'exit'` fires exactly once on real termination and only synchronous code is safe there.
2. **EIO/EPIPE storm guard**: swallowing dead-output-stream errors made the process a zombie (Ink's render loop throws once/sec on a dead PTY, each throw re-enters the same error handler, filling the crash log forever while a child process keeps running silently) — after 5 consecutive `EIO`/`EPIPE` in a row, it force-exits instead of continuing to swallow.
3. **Startup terminal clear**: full clear (`\x1b[2J\x1b[H\x1b[3J`, including scrollback) on desktop terminals, but explicitly **skipped** on Termux (prints just a blank line instead) so users can scroll back through prior output after reopening the app — a deliberate platform-specific UX carve-out.
4. **Heap/OOM self-defense**: a `startMemoryMonitor` with 3 tiers (`onWarn` → log a breadcrumb, `onHigh` → dump heap + log, `onCritical` → dump heap, log, then hard `process.exit(137)` — the SIGKILL-equivalent exit code, chosen specifically so post-mortem tooling can distinguish "we chose to die from OOM" from "the OS SIGKILL'd us"). The `onWarn` tier specifically exists to catch the *silent, sub-threshold* fast-heap-growth pattern that used to cause an untraceable death (issue #34095, same issue as the `config/limits.ts` VERBOSE_TRAIL comment above — this is the general-purpose backstop for the same underlying class of bug).
5. **Dashboard-embedded-PTY SIGINT carve-out**: when running inside a browser-embedded dashboard PTY (`DASHBOARD_TUI_MODE`), SIGINT is explicitly added to `ignoredSignals` because that host has no in-page restart path if the embedded process dies — better to eat a stray Ctrl+C (in case raw-mode briefly drops and the terminal driver converts the keystroke to a real signal) than to silently kill an unrecoverable child.
**Go note**: None of Node's PTY/mouse-mode-leak failure mode is directly relevant to a Go process (different signal/terminal-mode plumbing), but the *category* of bug is 100% relevant: Atlas should make sure enabling mouse-tracking/bracketed-paste/alternate-screen ANSI modes has a **guaranteed** disable-on-exit path that runs even on abnormal termination (panic, signal, or a plain `os.Exit`), not just on the "happy path" quit command — Go's `defer` doesn't run across `os.Exit`, so this needs either an explicit signal handler (`os/signal.Notify` for SIGINT/SIGTERM) plus a recovered-panic path that both call the same terminal-reset function, mirroring Hermes's "everything funnels through one idempotent `resetTerminalModes()`" design.

### `gatewayClient.ts` (944 lines) — Node child-process/WebSocket JSON-RPC transport
This is the process/transport layer connecting the TUI to a Python backend gateway (spawned as a child process over stdio, OR attached to via WebSocket, with an optional secondary "sidecar" WebSocket mirror for dashboard observers). Since Atlas is presumably a single Go binary that talks directly to LLM provider APIs (not a similar 2-process gateway architecture), most of this is not directly analogous, but several defensive patterns are broadly relevant to *any* long-lived client with a request/response protocol over a flaky transport:
- **Heartbeat-based dead-connection detection**: browser/undici `WebSocket` exposes no ping/pong ack API, so they roll their own JSON-RPC `gateway.ping` heartbeat every 15s (`WS_HEARTBEAT_INTERVAL_MS`) and force-close+reconnect if no ack within 45s (`WS_HEARTBEAT_DEAD_MS`) — catches silent drops (laptop sleep, idle proxy timeout, VPN reconnect) that never fire a `close` event.
- **Exponential backoff reconnect**: `RECONNECT_BASE_MS=1000` doubling up to `RECONNECT_MAX_MS=30000`, tracked via `reconnectAttempts`, explicitly cancelled on an intentional `kill()` (`disposed` flag) so it never fights a deliberate shutdown.
- **Identity-gated stale-event ignoring**: nearly every async callback (`proc.on('exit')`, `ws.addEventListener('close')`) checks `this.proc !== ownedProc` / `this.ws !== ws` before acting — because `start()` can replace the active transport while an old one is still tearing down, and without this guard a late event from the *old* transport could clear the *new* transport's ready-timer or reject the *new* transport's in-flight requests.
- **Buffered-event replay via `queueMicrotask`, not synchronous emit**: `drain()` defers replaying buffered startup events to a microtask specifically to avoid a documented React "Too many re-renders" crash (issue #36658) that happened when a `gateway.ready`→`session.info` event cascade fired synchronously during React's very first commit. Not applicable to Bubbletea (no React re-render-storm risk), but the general principle — "don't synchronously fire a cascade of state updates from inside a mount/init callback; defer to the next tick" — is broadly good practice.
- **URL redaction for logs**: `redactUrl` strips query strings and userinfo (`user:pass@`) from any gateway/sidecar URL before it's ever written to a log line or surfaced in a `gateway.start_timeout` payload — defense against leaking bearer tokens that ride in the query string.
- **Log-line size caps**: `MAX_LOG_LINE_BYTES=4096` truncates any single stderr/stdout line before storing it in the circular log buffer, `MAX_GATEWAY_LOG_LINES=200`/`MAX_BUFFERED_EVENTS=2000` cap total retained history — bounded memory for diagnostics regardless of how noisy the child process gets.
**Go note**: If Atlas has any long-lived network connection (streaming API calls, a local server, etc.), the heartbeat+exponential-backoff-reconnect pattern and the "identity-gate every async callback against the current active connection" pattern are both directly reusable regardless of language — the second one in particular prevents an entire class of "stale callback corrupts new state" bugs that are easy to introduce with goroutines outliving a reconnect.
